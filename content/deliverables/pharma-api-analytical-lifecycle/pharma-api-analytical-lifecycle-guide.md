# Pharma API Analytical & Lifecycle Control Guide

## Purpose

Connect one API quality attribute and intended decision to an analytical target profile, procedure development, method capability, sampling/data integrity, specification linkage, stability, transfer and lifecycle change.

## Applicability and limitations

Apply to a defined chemically synthesized small-molecule API, attribute, method use, lifecycle stage and market. Do not generalize to another product, matrix, method, instrument, site or modality. This guide supplies no method, condition, system-suitability criterion, validation design, limit, specification, stability condition, shelf life, transfer protocol or filing conclusion.

## Source basis

- `ICH-Q14`: science- and risk-based analytical procedure development and lifecycle management.
- `ICH-Q2-R2`: validation principles and performance characteristics.
- `ICH-Q6A`: specification concepts and development knowledge.
- `ICH-Q1A-R2`: stability testing context for drug substances/products.
- `ICH-Q7`: API laboratory and GMP context.
- `ICH-Q9-R1` and `ICH-Q10`: risk, knowledge, change and quality-system governance.
- `FDA-ANALYTICAL-PROCEDURES-2015`: analytical procedures and validation data context for identity, strength, quality, purity and potency.
- `FDA-PROCESS-VALIDATION-2011`: process-validation lifecycle context; it does not supply a product-specific validation design or conclusion.

## Workflow

1. Freeze product, form, process version, attribute, intended use, stage, market and Decision owner.
2. Define the analytical target profile and reportable decision need before choosing technology.
3. Map procedure principle, sample/reference system, capability, limitations, data lineage and system suitability.
4. Link attributes and method evidence to process/input controls and specification rationale.
5. Keep stability-indicating evidence, trends, packaging/sample context and commitments distinct from release testing.
6. Treat site/instrument/column/sample-preparation/reference changes as changed measurement systems requiring a bridge.
7. Record validation state, approved procedure, effective date, filing/reporting question and authorized implementation.
8. Close evidence and actions only with qualified review; preserve unresolved items.

## Critical review checklist

- Is the intended decision and attribute frozen before method selection?
- Does the analytical target profile state material, matrix, purpose and needed performance?
- Are method capability, sample/reference, system suitability and limitations explicit?
- Is each specification element linked to process, impurity, stability and analytical evidence?
- Is the method actually stability-indicating for the intended use, rather than assumed from release performance?
- Are transfer differences and bridge evidence explicit and versioned?
- Are data integrity, deviations, raw data, calculations and review responsibilities visible?
- Are lifecycle, filing and implementation decisions separately owned?
